# Requirements Document

## Introduction

A standalone personal Life Dashboard delivered as a single web page (`index.html` + one CSS file + one JavaScript file). It runs entirely in the browser with no server, no build step, and no frameworks. All persistent data lives in the browser's `localStorage`. The dashboard provides four widgets: a greeting panel, a Pomodoro focus timer, a to-do list, and a quick-links launcher. The page ships with light/dark theme support that follows the system colour-scheme preference on first load and allows the user to toggle it manually.

## Glossary

- **Dashboard**: The single-page web application described in this document, served from `index.html`.
- **LocalStorage**: The browser-native `window.localStorage` key/value store used for all persistence.
- **Greeting Widget**: The section that displays the current time, date, and a time-of-day greeting addressed to the user's name.
- **Focus Timer**: The Pomodoro-style countdown timer widget.
- **Work Session**: A countdown period defaulting to 25 minutes during which the user focuses on a task.
- **Break Session**: A countdown period defaulting to 5 minutes following a completed Work Session.
- **Cycle**: One Work Session followed by one Break Session.
- **To-Do List**: The widget for creating, editing, completing, and deleting tasks.
- **Task**: A single to-do item with a text label and a completion state.
- **Quick Links**: The widget displaying shortcut buttons that open saved URLs in a new browser tab.
- **Link Entry**: A single Quick Links item consisting of a label and a URL.
- **Quick Links Modal**: The dialog used to add and remove Link Entries.
- **Theme**: The visual colour scheme; either `light` or `dark`.
- **System Preference**: The operating-system-level colour-scheme setting detected via `prefers-color-scheme` media query.
- **Audio Alert**: A short beep or tone generated by the Web Audio API to signal a timer transition.
- **Duplicate Task**: A Task whose text label, after whitespace trimming and case-insensitive comparison, matches an existing incomplete Task.

## Requirements

### Requirement 1: Greeting Widget

**User Story:** As a user, I want to see the current time, date, and a personalised greeting so that I am oriented when I open the dashboard.

#### Acceptance Criteria

1. THE Dashboard SHALL display the current time in HH:MM format, updating every 60 seconds.
2. THE Dashboard SHALL display the current date in a human-readable format (e.g. "Monday, 20 November 2026").
3. WHEN the current local hour is between 05:00 and 11:59 inclusive, THE Greeting Widget SHALL display the greeting "Good Morning".
4. WHEN the current local hour is between 12:00 and 17:59 inclusive, THE Greeting Widget SHALL display the greeting "Good Afternoon".
5. WHEN the current local hour is between 18:00 and 20:59 inclusive, THE Greeting Widget SHALL display the greeting "Good Evening".
6. WHEN the current local hour is between 21:00 and 04:59 inclusive, THE Greeting Widget SHALL display the greeting "Good Night".
7. THE Greeting Widget SHALL append the stored user name to the greeting text when a user name is present in LocalStorage.
8. WHEN the user submits a non-empty name via the name-edit input, THE Greeting Widget SHALL save that name to LocalStorage under the key `userName` and display the updated greeting immediately.
9. IF the `userName` key is absent from LocalStorage, THEN THE Greeting Widget SHALL display the greeting without a name suffix.

### Requirement 2: Focus Timer

**User Story:** As a user, I want a Pomodoro countdown timer so that I can structure focused work sessions and breaks.

#### Acceptance Criteria

1. THE Focus Timer SHALL default to a 25-minute Work Session duration and a 5-minute Break Session duration on first load when no custom values are stored.
2. WHEN the user submits a valid integer between 1 and 60 (inclusive) as the Work Session duration, THE Focus Timer SHALL save that value to LocalStorage under the key `pomodoroWork` and apply it to the next session start.
3. WHEN the user submits a valid integer between 1 and 30 (inclusive) as the Break Session duration, THE Focus Timer SHALL save that value to LocalStorage under the key `pomodoroBreak` and apply it to the next session start.
4. THE Focus Timer SHALL display the remaining time as MM:SS, updating every second while the timer is running.
5. WHEN the user activates the Start button, THE Focus Timer SHALL begin counting down from the current Work Session duration if no session is in progress.
6. WHEN the user activates the Stop button while the timer is running, THE Focus Timer SHALL pause the countdown without resetting the remaining time.
7. WHEN the user activates the Start button while the timer is paused, THE Focus Timer SHALL resume the countdown from the paused remaining time.
8. WHEN the user activates the Reset button, THE Focus Timer SHALL stop the countdown and reset the display to the full Work Session duration.
9. WHEN the Work Session countdown reaches 00:00, THE Focus Timer SHALL emit an Audio Alert and automatically begin the Break Session countdown.
10. WHEN the Break Session countdown reaches 00:00, THE Focus Timer SHALL emit an Audio Alert and automatically begin a new Work Session countdown.
11. IF the submitted Work Session duration is not an integer between 1 and 60, THEN THE Focus Timer SHALL display an inline validation error and SHALL NOT save the value.
12. IF the submitted Break Session duration is not an integer between 1 and 30, THEN THE Focus Timer SHALL display an inline validation error and SHALL NOT save the value.

### Requirement 3: To-Do List

**User Story:** As a user, I want to manage a list of tasks so that I can track what needs to be done.

#### Acceptance Criteria

1. WHEN the user submits a non-empty task label via the add-task input, THE To-Do List SHALL add a new incomplete Task and save the updated list to LocalStorage under the key `tasks`.
2. IF the submitted task label matches an existing incomplete Task (case-insensitive, whitespace-trimmed), THEN THE To-Do List SHALL display an inline duplicate warning and SHALL NOT add the Task.
3. WHEN the user activates the complete control on a Task, THE To-Do List SHALL toggle that Task's completion state and save the updated list to LocalStorage.
4. WHEN the user activates the delete control on a Task, THE To-Do List SHALL remove that Task from the list and save the updated list to LocalStorage.
5. WHEN the user activates the edit control on a Task, THE To-Do List SHALL make the Task label inline-editable and save the updated label to LocalStorage when the user confirms the edit.
6. IF the user confirms an edit with an empty label, THEN THE To-Do List SHALL discard the edit and restore the original Task label.
7. THE To-Do List SHALL support sorting tasks by: (a) creation order (default), (b) alphabetical A–Z, (c) completed tasks last.
8. WHEN the user selects a sort option, THE To-Do List SHALL re-render the task list in the chosen order immediately without reloading the page.
9. THE To-Do List SHALL restore all saved Tasks from LocalStorage on page load and render them in the previously selected sort order.

### Requirement 4: Quick Links

**User Story:** As a user, I want shortcut buttons to my favourite websites so that I can open them without typing URLs.

#### Acceptance Criteria

1. THE Dashboard SHALL display a Quick Links section containing one button per saved Link Entry.
2. WHEN the user activates a Quick Links button, THE Dashboard SHALL open the corresponding URL in a new browser tab.
3. WHEN the user opens the Quick Links Modal, THE Dashboard SHALL display all existing Link Entries as an editable list within the modal.
4. WHEN the user submits a valid label and a valid URL in the Quick Links Modal, THE Dashboard SHALL add a new Link Entry, save the updated list to LocalStorage under the key `quickLinks`, close the modal, and re-render the Quick Links section.
5. IF the submitted URL does not begin with `http://` or `https://`, THEN THE Dashboard SHALL display an inline validation error in the modal and SHALL NOT save the entry.
6. IF the submitted label is empty, THEN THE Dashboard SHALL display an inline validation error in the modal and SHALL NOT save the entry.
7. WHEN the user activates the remove control for a Link Entry in the Quick Links Modal, THE Dashboard SHALL remove that entry, save the updated list to LocalStorage, and re-render the modal list.
8. THE Dashboard SHALL restore all saved Link Entries from LocalStorage on page load and render the corresponding Quick Links buttons.
9. WHEN the user activates the close control or clicks outside the Quick Links Modal, THE Dashboard SHALL close the modal without making changes.

---

### Requirement 5: Light / Dark Theme

**User Story:** As a user, I want the dashboard to respect my system colour scheme and let me toggle it manually so that the interface is comfortable in any lighting condition.

#### Acceptance Criteria

1. WHEN the Dashboard loads and no theme preference is stored in LocalStorage, THE Dashboard SHALL apply the `dark` theme if the system reports `prefers-color-scheme: dark`, and the `light` theme otherwise.
2. WHEN the user activates the theme-toggle control, THE Dashboard SHALL switch to the opposite theme, save the new theme value (`light` or `dark`) to LocalStorage under the key `theme`, and apply the change immediately without reloading the page.
3. WHEN the Dashboard loads and a `theme` value is present in LocalStorage, THE Dashboard SHALL apply that stored theme, ignoring the current system preference.

---

### Requirement 6: Technical Constraints

**User Story:** As a developer, I want the project to follow a strict file and technology structure so that the codebase remains simple and maintainable.

#### Acceptance Criteria

1. THE Dashboard SHALL be implemented using only HTML, CSS, and Vanilla JavaScript with no external frameworks, libraries, or build tools.
2. THE Dashboard SHALL contain exactly one CSS file located at `css/style.css`.
3. THE Dashboard SHALL contain exactly one JavaScript file located at `js/app.js`.
4. THE Dashboard SHALL be served from `index.html` at the project root.
5. THE Dashboard SHALL function correctly when opened as a local file via `file://` protocol in Chrome, Firefox, Edge, and Safari without any server.
6. THE Dashboard SHALL store all persistent data exclusively in `window.localStorage`; no cookies, `sessionStorage`, IndexedDB, or server calls SHALL be used for persistence.
